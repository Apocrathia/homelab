# Trivy known false positives

Catalog of Trivy IaC misconfig findings that fire on homelab manifests but are
not actionable security issues. Each entry explains what triggers the finding,
why it's a false positive, and how the actual sensitive data is managed.

Add new entries here when a finding is triaged and confirmed benign. Do not
re-file the same finding as an issue unless the underlying assumption changes
(e.g. Trivy's check logic is updated and the finding becomes genuine).

## Catalog

| ID       | Finding                | Triggers on                    | Actual secret storage              |
| -------- | ---------------------- | ------------------------------ | ---------------------------------- |
| KSV-0109 | ConfigMap with secrets | Authentik blueprint ConfigMaps | 1Password operator-managed Secrets |

## KSV-0109 — Authentik blueprint ConfigMaps

### What triggers it

Trivy's `KSV-0109` (ConfigMap with secrets, `AVD-KSV-0109`) fires on every
Authentik blueprint ConfigMap in the cluster — `authentik-blueprint-litellm`
and the ones generated by `generic-app` chart kustomizations alike.

The heuristic scans ConfigMap data for strings matching secret patterns. It
hits on Authentik OIDC provider field **names** inside the embedded blueprint
YAML:

- `include_claims_in_id_token` (boolean: `true`)
- `access_token_validity` (duration: `"minutes=5"`)
- `refresh_token_validity` (duration: `"days=30"`)
- `token_validity` (duration: `"days=30"`)
- `signing_key` (resource reference: `!Find [...]`)
- `client_type` (string: `"confidential"`)

Every matched value is a boolean, duration string, or Authentik resource
reference — not a credential, token, or key.

### Where the real secrets live

The OIDC client secret and all provider API keys are stored in a
1Password-operator-managed `Secret`:

```yaml
# Example: litellm-secrets (OnePasswordItem)
apiVersion: onepassword.com/v1
kind: OnePasswordItem
metadata:
  name: litellm-secrets
  namespace: litellm
spec:
  itemPath: "vaults/Secrets/items/litellm-secrets"
```

The HelmRelease references these via `valuesFrom` (kind: Secret) and
`environmentSecrets`. The `oidc-client-secret` is never written to a ConfigMap
or committed to Git.

**Verified:** read-only cluster probe of the live `litellm` namespace
confirmed the `authentik-blueprint-litellm` ConfigMap contains only
provider/application metadata, and the `litellm-secrets` Secret holds all
actual credentials.

### Why it can't be suppressed with inline comments

Trivy supports `#trivy:ignore:<ID>` inline comments, but:

1. They are **non-functional for Kubernetes YAML** on trivy 0.74.0 (tested
   with a trivial privileged-Pod control — the comment never suppressed the
   finding).
2. The ConfigMap is **generated by kustomize** (`configMapGenerator`) — it
   does not exist in any source file, and kustomize does not propagate
   comments into generated output. There is no source-side location to attach
   a comment.

### Why it can't be suppressed in `.trivyignore.yaml`

Path-scoped ignore entries match the **scanned filename**, not the resource
name. CI scans only changed raw files (`authentik-blueprint.yaml`), which
are not parsed as Kubernetes objects and produce no KSV-0109 findings.
Rendered-build scans (local review) use ad-hoc filenames under `.scratch/`,
making a stable path pin fragile. A path-less (global) entry would suppress
KSV-0109 repo-wide, hiding genuine ConfigMap-with-secrets issues elsewhere.

### Disposition

**Known false positive.** Documented here as the definitive triage record.
Do not re-file, do not treat as blocking in CI or local review, and do not
add a blanket KSV-0109 suppression to `.trivyignore.yaml`.

## Triage procedure

When a new Trivy finding appears:

1. **Identify the resource** — is it a ConfigMap, Secret, Role, Deployment?
2. **Check values** — do the matched strings contain actual secrets, or are
   they field names / comments / placeholder references?
3. **Trace actual secrets** — where are the real credentials stored? Confirm
   the 1PasswordItem → Secret → HelmRelease `valuesFrom` chain.
4. **If false positive:** add an entry to the catalog above and close.
5. **If genuine:** file a `docs/issues/` entry with the finding ID, resource
   path, and remediation steps.
